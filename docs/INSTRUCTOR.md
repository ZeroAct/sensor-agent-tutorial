## 진행자가 되는 방식

오늘 권위는 “베어링 결함주파수”가 아니라 **도구와 언어를 설계하는 일**에 둡니다.

말해도 되는 것

- LLM은 센서에 직접 연결되어 있지 않다
- MCP는 도구 호출의 계약이다
- Skill은 그 계약을 현장에서 어떻게 쓰는지 적은 Markdown이다
- 숫자는 도구에서 오고, 조치는 사람이 한다

말하지 말 것

- “RMS 7.0이면 베어링이 80% 남았다”
- “이 모델이 예지보전을 대체한다”
- FFT, 엔벨로프, ISO 등급을 즉석 강의로 확장
- 수강생 키를 채팅창이나 슬라이드에 붙여 넣고 진행

모르면 “오늘은 더미 임계값입니다. 현장 기준은 설비마다 다릅니다.”가 정답입니다.

## 블록별 말하기 포인트

### 이론 1 — 예지보전 개요 (~8분)

**목표:** 사후/예방/예지를 **한 장**으로 구분하고, AI를 ‘고치는 주체’가 아니라 **루프의 설명자**로 위치시킨다.

#### 말하기 포인트 (분 배분)

1. **(2분) 세 칸 칠판**
   - 사후: 멈춘 뒤 고친다 → 단순, 다운타임·비용 큼
   - 예방: 달력으로 간다 → 과보전 + 미보전 동시 발생
   - 예지: 상태 신호가 나빠지면 간다 → **신호 + 판단 규칙**이 필요
2. **(3분) 예지의 한 문장**
   - “고장이 나기 전에, 상태 신호를 보고, **사람이 개입할 시간을 버는** 일.”
   - AI는 가운데가 아니라 루프 **오른쪽**: 감지 → 전달 → 조회 → 설명 → **결정(사람)**
3. **(2분) 현업 언어 번역**
   - “스마트 공장 = AI가 알아서”가 아니라 “측정 → 규칙 → 사람”
   - 오늘 숫자 = 학습용 더미. 실제 진단 절차 아님
4. **(1분) 체크포인트**

#### 비유

- **건강검진**: 사후=응급실, 예방=매년 같은 날 피검사, 예지=혈압이 계속 오르면 의사에게 예약
- **네비게이션**: 센서=GPS, 챗봇=길 안내 멘트, 운전=사람. 네비가 핸들을 돌리지 않음

#### must-say

- 예지보전 = 감지→판단→**사람 조치** 루프
- AI/챗봇은 조치자가 아님
- 오늘은 더미 데이터; 현장 기준으로 쓰지 말 것

#### must-not-say

- “이 모델이 예지보전을 대체한다”
- 잔여수명(%), 베어링 결함주파수, ISO 등급 즉석 강의
- “AI가 설비를 고친다”

#### 체크포인트

1. “예방보전과 예지보전의 결정적 차이는?” → **달력 vs 상태 신호**
2. “루프에서 AI가 하면 안 되는 단계는?” → **최종 기동/정지·정비 결정**

### 이론 2 — 센서 이상 시나리오 (~10분)

**목표:** 가상 플랜트 스토리로 ‘이상(anomaly)’을 현업 언어에 붙이고, 오늘 이상은 **단순 임계값(threshold)** 임을 고정한다.

#### 말하기 포인트 (분 배분)

1. **(2분) 무대 세팅**
   - 냉각수 펌프 A, HVAC 팬 B
   - 주인공: `pump-a-de` (구동측). 조연: `pump-a-nde`, `fan-b-motor`
2. **(3분) RMS를 ‘크기 한 숫자’로만**
   - 정상 ≈ 2 mm/s (더미)
   - 경고 4.5 / 이상 7.0 = **수업용 숫자**, 현장 기준 아님
   - “왜 RMS?” → “한 숫자로 크기를 말하려고. 주파수 분석은 오늘 범위 밖.”
3. **(3분) 이상 = 임계값 초과 (딥러닝 아님)**
   - 45초마다 스파이크 → 데모가 안 죽게 설계됨
   - 현업 언어: RMS↑ = “상태가 나빠지고 있다” (원인 단정 금지)
   - normal / warning / anomaly 읽는 법 (안전 인증 아님)
4. **(2분) 체크 + 실습 예고**
   - 나중에 챗봇 답이 `/demo/sensors` JSON과 다르면 → 모델이 추측한 것

#### 비유

- **체온계**: 38.5°C는 ‘뜨겁다’는 신호. 원인 진단은 체온계가 하지 않음
- **과속 카메라**: 제한 초과 = 이벤트. 왜 밟았는지는 모름
- **신호등**: 노랑=warning, 빨강=anomaly (오늘은 더미일 수 있음)

#### must-say

- 오늘 이상 = **코드의 임계값(threshold)**. 모델이 탐지한 것 아님
- 숫자는 수업용; 현장 기준은 설비마다 다름
- 원인(베어링/언밸런스 등)을 지어내지 말 것

#### must-not-say

- “RMS 7.0이면 베어링이 80% 남았다”
- FFT, 엔벨로프, 결함주파수 확장 강의
- 실설비 정비 절차처럼 말하기

#### 체크포인트

1. “오늘 실습의 anomaly는 누가/무엇이 만드나?” → **더미 센서의 임계값 규칙** (LLM 아님)
2. “warning인데 추세 도구가 없으면 Skill이 뭐라고 해야 하나?” → **없다 / 한계를 말할 것**

### 이론 3 — 챗봇 + MCP + Skills (~15분)

**목표:** ‘챗봇만’의 한계 → MCP(도구 계약) → Skill(Markdown 플레이북) 순서로 **세 번 반복**. 도구는 3개만.

#### 말하기 포인트 (분 배분)

1. **(4분) 막히는 지점 1 — 챗봇만**
   - LLM = 어제 인터넷 지식. **지금 펌프 값이 아님**
   - 비유: 도서관 사서에게 “우리 공장 펌프 지금 진동?” → 책만 있고 현장 계측기 없음
2. **(5분) 막히는 지점 2 — MCP**
   - MCP = 모델이 부를 수 있는 **도구의 표준 연결/계약**
   - 오늘 도구 3개만:
     - `list_sensors` — 목록·상태 (기동/정지 아님)
     - `get_vibration_reading` — 최신 값 (스펙트럼/FFT 아님)
     - `get_recent_anomalies` — 최근 이상 (정비 지시 아님)
   - 비유: **USB 포트** — 꽂힌 것만 사용
   - 데이터 경로: 더미 진동 → MQTT → MCP :8000 → 챗봇(Open WebUI)
3. **(4분) 막히는 지점 3 — Skills**
   - 도구가 있어도 모델은 대충 요약 / 정비 명령 / **없는 센서 발명** 가능
   - Skill = 도구를 *어떻게* 쓸지 적은 **Markdown 플레이북**. 코드 아님
   - 비유: **항공 체크리스트**
   - Open WebUI UI 디테일은 실습에서 (여기서 깊게 X)
4. **(2분) 체크**

#### 비유

- 사서(챗봇만) / USB 포트(MCP) / 항공 체크리스트(Skill) — 위 말하기 포인트에 포함

#### must-say

- LLM은 플랜트에 직접 연결되지 않음
- MCP = 도구 호출 계약; Skill = 현장 절차를 고정하는 Markdown
- 도구는 **3개뿐**. 네 번째 즉석 제안 금지
- 숫자는 도구에서, 조치는 사람

#### must-not-say

- “MCP 대신 아무 API나 프롬프트에 키 넣고 호출”
- Python Function으로 도구 작성 권장 (오늘 범위 밖)
- 도구를 많이 만드는 게 목표라고 말하기

#### 체크포인트

1. “챗봇만으로 부족한 이유는?” → **현재 현장 값에 연결되어 있지 않음**
2. “MCP와 Skill 차이는 한 줄로?” → **MCP=무엇을 부를 수 있나 / Skill=어떻게·어떤 말로 쓰나**

### 이론 4 — Skill / MCP 설계 원칙 (~17분, 가장 깊게) ★핵심

**목표:** ‘작게, 이름 분명, 최소 권한, 숫자 발명 금지, 정비는 사람’을 **Skill 파일 화면**으로 체감. 이론의 무게 중심.

#### 말하기 포인트 (분 배분)

1. **(3분) Skill 4칸** — “친절한 전문가” 한 줄 ≠ Skill
   - 역할 / 언제 쓰나 / 절차 / 출력 형식
   - **화면 공유:** [`playground/skills/vibration-pdm.md`](../playground/skills/vibration-pdm.md) 스크롤
2. **(3분) 도구는 동사+명사, 작게**
   - 좋은 예: `list_sensors`, `get_vibration_reading`, `get_recent_anomalies`
   - 나쁜 예: `do_everything`, `analyze_plant`
   - 비유: 만능 리모컨 vs TV 버튼 3개
3. **(3분) 최소 권한**
   - 오늘 = **읽기만**. 펌프 정지 도구 **일부러 없음**
   - 비유: 인턴 조회 배지 vs 마스터키
4. **(3분) 그라운딩 (숫자 발명 금지)**
   - 도구 실패 시 정답: “지금은 값을 못 읽었다”
   - 오답: 그럴듯한 `2.3 mm/s`
   - 절차: 도구 호출 **전**에 숫자 말하지 말 것; `rms_mm_s` / `status` / `ts` **그대로 인용**
   - 비유: 영수증 없이 경비 청구 금지. 도구 JSON = 영수증
5. **(3분) 사람은 최종 결정자 + 안티패턴**
   - 권고 끝: “현장 확인 전 기동/정지 금지”
   - 안티패턴: 만능 도구 / 비밀 키를 프롬프트에 / Python Skill / 모델에게 정비 승인 / 없는 sensor_id 생성
6. **(2분) 회고 씨앗**
   - “우리 팀에 챗봇을 붙인다면, 모델에게 **시키지 않을** 도구는 ○○이다.”

#### 비유

- 만능 리모컨 vs TV 버튼 3개 (작은 도구)
- 인턴 조회 배지 vs 마스터키 (최소 권한)
- 영수증 없이 경비 청구 금지 (그라운딩)

#### must-say

- 오늘 이론의 핵심은 **도구를 많이 만드는 법이 아니라 제한하는 법**
- Skill 4칸 + 작은 도구 + 읽기 전용 + 숫자=도구 + 결정=사람
- 실패 시 추정 금지; 한계를 말하는 것이 전문성

#### must-not-say

- “일단 만능 분석 도구 하나면 된다”
- 키/내부 URL을 프롬프트·슬라이드에 노출
- 모델이 정비 승인·정지 명령을 내려도 된다고 암시

#### 체크포인트

1. “Skill이 한 줄 페르소나와 다른 점은?” → **역할·절차·출력·금지까지 고정**
2. “도구가 실패했을 때 좋은 답 / 나쁜 답은?” → 좋은: 못 읽었다 / 나쁜: 가짜 RMS

## 실습 진행 (50분)

### 환경 (15분)

수강생 화면이 제각각입니다. **한 명령으로 통일**합니다.

```bash
cd playground
cp .env.example .env
# 진행자가 프로젝터에 .env 키 이름을 보여 주고, 값만 각자 입력
./scripts/up.sh
```

성공 신호

- `open-webui` 8080
- `mcp-server` 8000
- `dummy-sensor`가 `publishing` 로그

실패한 사람: 로컬 Docker 문제가 많으면 Codespaces로 즉시 이동. 디버깅에 10분을 쓰지 않습니다.

### 연결 (15분)

화면을 천천히 클릭합니다. 관리자 메뉴 이름이 버전마다 조금 다릅니다.

1. Open WebUI → **Admin Settings → Integrations** (또는 외부 도구)
2. Add Server → 타입 **MCP (Streamable HTTP)**  (OpenAPI가 아님)
3. URL: `http://mcp-server:8000/mcp`  
   브라우저가 Codespaces 호스트에서 MCP를 직접 넣을 때만 `http://localhost:8000/mcp`
4. Auth: **None** (Bearer 빈 칸은 실패 사례가 많음)
5. 채팅창에서 해당 MCP 도구를 켠다
6. Skill Markdown을 **Workspace → Skills** 또는 **Prompt**에 그대로 붙여 넣는다  
   Python Function을 만들지 말라고 한 번 더 말한다

`docker-compose`는 `TOOL_SERVER_CONNECTIONS`로 MCP를 미리 넣으려 합니다.
버전에 따라 UI에서 한 번 Save가 필요할 수 있습니다. 당황하지 말고 위 절차를 반복.

### 질문 3개 (10분)

수강생이 직접 타이핑하게 합니다.

1. `지금 플랜트에 진동 센서가 뭐가 있나요?`
2. `pump-a-de 최신 값 알려 주세요. 숫자와 시각을 그대로.`
3. `최근 이상만 짧게 요약하고, 지금 펌프를 멈춰야 하는지는 사람이 결정한다고 적어 주세요.`

좋은 답의 조건 (채점 기준을 공개)

- 센서 ID가 `pump-a-de` / `pump-a-nde` / `fan-b-motor` 중이다
- RMS 숫자가 `/demo/sensors`와 크게 다르지 않다 (시점이 몇 초 차일 수 있음)
- “정지하세요”를 명령조로 쓰지 않는다

### 해석과 리스크 (10분)

같은 답을 현장 언어로 다시 읽습니다.

- normal → 지금은 수업용 기준에서 평온
- warning → 추세를 더 보자 (오늘 실습은 추세 도구가 없음 → Skill이 한계를 말해야 함)
- anomaly → 값이 튀었다. **더미 스파이크일 수 있다**고 정직하게

리스크 두 개를 경험과 연결합니다.

- 429가 난 사람 → 창피하지 않다. `curl` JSON을 읽으면 실습 목표 달성
- 로그인·관리자 화면에서 막힌 사람 → 그래서 워크숍은 인증을 끈다. 사내 도입 시 이 비용이 본게임

## 실패 복구 (플랜 B / C)

| 증상 | 원인 후보 | 진행자가 할 일 |
| --- | --- | --- |
| Open WebUI가 모델 목록 없음 | `.env` 키/베이스 URL | 키 없이 실습하지 말 것. 예제 값을 다시 보여 주기 |
| 채팅 429 / 빈 답 | 무료 한도 | `/demo/sensors` 화면 공유. 수업 계속 |
| MCP 연결 실패 | 타입 OpenAPI, URL localhost, Bearer 공란 | Streamable HTTP, `http://mcp-server:8000/mcp`, Auth None |
| 도구를 안 부름 | 채팅에서 MCP 토글 Off, Skill 없음 | 토글 + Skill 붙여 넣기 + “도구를 먼저 호출해” 한 줄 |
| 센서가 항상 normal | 이상 주기 전에 질문 | 45초 대기 후 `get_recent_anomalies` 재호출 |
| Codespaces 8080이 안 열림 | 포트 포워드 | Ports 탭에서 8080 Public/브라우저 열기 |
| compose가 메모리로 죽음 | 2 GB Codespaces | 8 GB로 리빌드. 진행자 데모만 공유 |

LLM이 전부 죽어도 **성공 기준**은 다음이면 충분합니다.

1. 네 컨테이너가 Up
2. `/health`가 ok
3. Skill Markdown을 읽고 “이 문장이 모델 행동을 제한한다”고 말할 수 있다

## 예상 질문과 짧은 답

**Q. 실제 공장 MQTT에 그냥 붙이면 되나요?**  
A. 프로토콜은 같아도 권한·네트워크·안전이 다릅니다. 오늘은 더미입니다.

**Q. 이상 탐지를 모델이 하면 안 되나요?**  
A. 할 수는 있습니다. 오늘은 의도적으로 임계값을 코드에 두었습니다. 모델은 설명자입니다.

**Q. Skill을 영어로 써야 하나요?**  
A. 모델이 잘 따르는 언어면 됩니다. 오늘 수강생·답이 한국어라 한국어 Skill입니다.

**Q. MCP 대신 Open WebUI Function(Python)은요?**  
A. 가능하지만 오늘 범위 밖입니다. 운영 팀이 파이썬을 안 고쳐도 되게 Markdown으로 제한했습니다.

**Q. 무료 키가 없으면요?**  
A. 짝을 이루거나 진행자 화면을 봅니다. JSON 데모로 목표의 80%는 전달됩니다. 키를 공유하지는 않습니다(한도·보안).
